# ADR: scoped GitHub event subscriptions and agent delivery

Decision: implement MVP 35/36 as explicit per-PR subscriptions, off by default. A verified PR offers independent consent to notify on failing checks and to wake this chat on passing checks. Failures never wake a stopped worker. PR/check/auto-merge webhooks update cards promptly; polling reconciles missed deliveries. No remote hook creation, permission upgrade, merge or branch-rule mutation is part of this feature.

The deployment operator configures a high-entropy `AGENT_GITHUB_WEBHOOK_SECRET` and registers `/webhooks/github` separately. Until then the UI says polling only. Authenticate bounded raw bytes using HMAC-SHA256 and constant-time comparison before parsing. Persist only normalized event hints, signed-body digest and delivery bookkeeping, not arbitrary PR text. A signed event is a refresh hint: current PR and aggregate checks must be read with the selected company's exact saved GitHub connection. The webhook cannot select an owner or grant access. Delivery-ID dedupe is supplemented by semantic current-head transition dedupe because headers themselves are not included in GitHub's body signature.

Subscriptions bind actual owner/chat/company/GitHub connection and account identity, numeric repository identity/name and PR, environment ID, provider and named agent account identity. Scope is revalidated from durable records, not speculative ChatStore cache. Absence, disconnection, deletion, archive or changed binding blocks dispatch. No legacy/anonymous identity is guessed. Environment revision changes do not alone invalidate an unchanged environment identity and current admission.

Only fresh canonical aggregate checks on the current PR head can create notifications. Empty, unknown or stale checks cannot wake a worker. A head change or out-of-order delivery cannot reuse a prior head's result. Check transitions and agent-event receipts persist independently of disposable workers. Busy agents are not interrupted: notifications join the existing FIFO. A manual Stop already in flight wins every pending dispatch. A later passing transition may wake only a stopped chat with explicit passing-check consent; this does not resume an independently paused user queue.

Native execution cannot be made exactly-once by a local database transaction. Persist the dispatch claim before native submission; after an ambiguous crash, retain an explicit uncertain receipt and never automatically replay that turn. Pending receipts may be recovered, and scope/Stop checks still apply. The UI reports blocked/uncertain delivery and requires explicit review before retry, without impersonating an ordinary user instruction. The agent receives a fixed, labeled GitHub event containing only verified identifiers/status, not executable instructions or untrusted PR/check log text.

Storage uses narrow owned-COMMIT transactions and sorted per-record locks, including absent revocation markers and the exact GitHub credential record. No external I/O or async transition callback executes inside a transaction. Encrypted webhook records are at most 4 KiB, with an atomic 1,000-record total cap (including completed receipts); completed receipts expire after seven days. Capacity exhaustion returns 503 rather than silently dropping a delivery; polling continues reconciling status. Event state is bounded to 256 KiB per chat, 30 subscriptions and 20 unresolved deliveries plus bounded terminal history. Existing credentials are never returned in public event state.

Exactly one event dispatcher owns a dedicated PostgreSQL session advisory lock; no long transaction is retained. Only its opaque trusted handle may recover interrupted dispatches, claim new work or pass final native admission. Transactions verify both the lock-owning backend PID and its startup identity, and a lost session fences the handle. Another application instance can ingest signed hints and update consent but cannot turn an active dispatch into retryable uncertainty. A standby needs a subsequent explicit initialization/acquisition (or restart) after ownership becomes available; automatic failover is not claimed. After owner loss, already accepted native work remains inherently ambiguous: recovery does not replay it, and explicit retry warns that work may repeat.

This exclusive event dispatcher is not a general highly available RuntimeManager. Manual Stop fencing is verified in the controller owning the chat's runtime; its persisted start/end cutoff uses that controller's clock. Cross-controller Stop routing, concurrent runtime ownership and clock-skew-proof cancellation require a broader durable lifecycle protocol and are not claimed by this component.

Current admission preserves the later explicit user requirement: one company per GitHub connection, only named agent accounts shared across companies, and company-separated chats. This supersedes the earlier item 21 wording; no multi-company GitHub fallback is introduced. Disabling an existing event subscription is an owner-and-revision-only local operation and does not require working GitHub credentials, a connected agent or an open PR. Consent and delivery-review writes bind the captured authenticated owner and exact server-resolved session row; session deletion shares the admission lock, so logout during a lock wait denies the write. Previously valid subscriptions do not require the owner to remain logged in for background event delivery.

Acceptance: loopback signed-webhook HTTP tests, replay/conflicting delivery IDs, current-head/out-of-order/fork hints, polling reconciliation, real PostgreSQL reopen/CAS/commit failure, owner/company/account/repository revocation races, busy FIFO, manual Stop, stopped failure vs authorized pass wake, paused user queue, restart uncertainty, and responsive browser opt-in/status. Fixtures use synthetic credentials and fake providers; no real GitHub hooks, model turns or cloud mutations.
